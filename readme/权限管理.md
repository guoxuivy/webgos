# RBAC权限管理

## 1. 概述

RBAC（Role-Based Access Control，基于角色的访问控制）是系统安全的重要组成部分。本系统采用 RBAC 模型实现权限管理，通过用户、角色、菜单、权限点的多级关联，实现灵活的权限控制。

### 1.1 核心概念

- **用户（User）**：系统的使用者，可被分配一个或多个角色
- **角色（RBACRole）**：一组权限的集合，通过关联菜单间接获得权限
- **菜单（Menu）**：前端导航菜单，可绑定若干权限点
- **权限点（路由投影）**：系统中最小的访问控制单元，对应一个接口（path + method）。权限点不再持久化到数据库，而是实时从已注册路由（gin `Routes()`）投影得到，键为 `path#method`，确保永远等于真实存在的路由

权限收敛路径：`用户 → 角色 → 菜单 → 权限点`。

### 1.2 RBAC模型特点

- 灵活性：用户通过角色继承菜单与权限，无需直接分配权限
- 可扩展性：可方便添加角色、菜单、权限点
- 易管理：通过角色管理权限，简化权限分配过程

## 2. 数据模型设计

### 2.1 用户模型（User）

```go
type User struct {
    BaseFields
    Username     string     `gorm:"unique" json:"username"`
    // ... 其他字段 ...
    Roles        []RBACRole `gorm:"many2many:rbac_user_roles;" json:"roles"`
}
```

### 2.2 角色模型（RBACRole）

```go
type RBACRole struct {
    BaseFields
    Name        string    `gorm:"size:50;unique" json:"name"`
    Remark      string    `gorm:"size:200" json:"remark"`
    Status      int       `gorm:"default:1;comment:状态 0-禁用 1-启用" json:"status"`
    Users       []User    `gorm:"many2many:rbac_user_roles;" json:"-"`
    Menus       []Menu    `gorm:"many2many:rbac_role_menus" json:"-"`
    MenuIDs     []int     `gorm:"-" json:"menu_ids"`
}
```

> 注意：角色不直接关联权限点，而是通过 `Menus` 间接获得权限；原 `Permissions` 与 `role_permissions` 关联已重构为 `rbac_role_menus` + `rbac_menu_permissions`。

### 2.3 权限点（实时路由投影，非持久化实体）

权限点不再对应数据库表，而是在管理端列出时实时从已注册路由读取：

- 键（perm_key）：`path#method`（path 小写、method 大写），由 `models.BuildPermKey` 统一生成
- 描述：路由注册时在 `RouterWrapper` 写入 `models.RouteDescriptions` 的文案
- 列表接口 `GET /api/rbac/permissions` 直接遍历 `models.RouteDescriptions` 返回，零数据库查询

菜单与权限点的绑定关系仍持久化在 `rbac_menu_permissions` 表（见 2.4）。

### 2.4 关联表

| 关联表 | 字段 | 说明 |
|--------|------|------|
| rbac_user_roles | user_id, rbac_role_id | 用户-角色 |
| rbac_role_menus | rbac_role_id, menu_id | 角色-菜单 |
| rbac_menu_permissions | menu_id, perm_key, description | 菜单-权限键（perm_key = path#method） |

## 3. 权限点实时化机制

权限点不再持久化，而是实时从已注册路由投影得到，彻底避免代码与数据库漂移。

### 3.1 权限键规则

- 权限点键（perm_key）格式为 `路径#方法`，例如 `/api/products#GET`（路径小写、方法大写，由 `models.BuildPermKey` 统一生成：`strings.ToLower(path) + "#" + strings.ToUpper(method)`）。
- RBAC 中间件鉴权时直接用 `perm.PermKey` 作为权限集合 key，请求侧构造的校验 key 为 `当前路径(小写)#方法(大写)`，二者分隔符与大小写规则完全一致。
- 示例权限点：
  - 路径 `/api/products`，方法 `GET` → perm_key=`/api/products#GET`，校验 key=`/api/products#GET`

### 3.2 实时读取流程

1. 路由注册时，`RouterWrapper` 将路由描述文案写入内存表 `models.RouteDescriptions`（key = `path#method`）。
2. 管理端 `GET /api/rbac/permissions` 直接遍历 `models.RouteDescriptions` 返回全部权限点，零数据库查询。
3. 请求链路鉴权仍使用 `c.FullPath()`（零成本），不受实时化影响。

> 说明：早期版本的 `SyncPermissions` 启动同步与 `AutoRBACPoint` 配置已移除，权限点始终等于真实路由，无需手动维护，也无需启动同步。

### 3.3 路径处理规范

- 所有路径统一转换为小写
- 去除重复的斜杠
- 保持路径结构清晰

## 4. 权限验证流程

### 4.1 JWT认证

1. 用户登录成功后，系统生成 JWT 令牌并返回给客户端
2. 客户端在后续请求中通过 Authorization 头携带令牌
3. 服务端 JWT 中间件验证令牌并设置 `user_id` 到上下文

### 4.2 权限检查（RBAC 中间件）

1. 从上下文获取 `user_id`；若为空返回 401 Unauthorized。
2. 若用户为超管（`config.GlobalConfig.SuperAccount`），直接放行。
3. 尝试从缓存（`permission:{user_id}`，有效期 5 分钟）读取用户权限集合；未命中则从 `user → roles → menus → permissions` 归集。
4. 以 `perm.PermKey`（即 `路径(小写)#方法(大写)`）构建用户权限集合，请求侧构造校验 key `当前路径(小写)#方法(大写)`（`currentPath + "#" + currentMethod`），若集合包含该 key 则放行，否则返回 403 Forbidden。
5. 角色/菜单变更时会失效相关用户的权限缓存，确保变更及时生效。

## 5. API接口

### 5.1 角色管理

#### 创建角色

```bash
POST /api/rbac/role
{
  "name": "管理员",
  "remark": "系统管理员角色",
  "status": 1,
  "menu_ids": [1, 2]
}
```

#### 编辑角色

```bash
POST /api/rbac/edit_role
{
  "id": 1,
  "name": "管理员",
  "remark": "系统管理员角色",
  "status": 1,
  "menu_ids": [1, 2, 3]
}
```

#### 获取角色详情

```bash
GET /api/rbac/role/{id}
```

#### 获取角色列表

```bash
GET /api/rbac/roles
```

#### 获取用户角色

```bash
GET /api/rbac/user_roles/{id}
```

#### 获取角色权限（所绑菜单下权限点去重集合）

```bash
GET /api/rbac/role_permissions/{id}
```

### 5.2 关系分配

#### 分配角色给用户

```bash
POST /api/rbac/assign_roles
{
  "user_id": 1,
  "role_ids": [1, 2]
}
```

#### 分配菜单给角色

```bash
POST /api/rbac/assign_menus
{
  "role_id": 1,
  "menu_ids": [1, 2, 3]
}
```

#### 绑定权限键到菜单（Replace 语义，全量替换该菜单的权限键）

```bash
POST /api/menu/permissions
{
  "menu_id": 1,
  "perm_keys": ["/api/products#GET", "/api/products#POST"]
}
```

#### 获取菜单绑定的权限键

```bash
GET /api/menu/permissions/{id}
```

#### 解绑单个菜单权限键

```bash
DELETE /api/rbac/permission
{
  "menu_id": 1,
  "perm_key": "/api/products#GET"
}
```

## 6. 最佳实践

### 6.1 角色设计原则

- 遵循最小权限原则，只为角色分配完成工作所需的最少菜单/权限
- 角色命名应具有明确的业务含义
- 避免为每个用户创建单独的角色

### 6.2 权限管理

- 权限点实时从路由投影得到，始终与路由一致，无需手动维护
- 通过 `POST /api/menu/permissions`（AssignPermissionsToMenu）显式维护菜单与权限键的归属
- 通过描述性文字清楚表达每个权限点的作用
- 定期审查角色-菜单-权限分配，确保符合安全要求
